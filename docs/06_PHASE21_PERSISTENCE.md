# Phase 2.1 persistence layer

## Scope and implementation plan

Implement the ten existing tables as JPA entities and provide repository access for the core retrieval paths. Keep Java 21 as the compilation target and use the existing Spring Boot/JPA dependencies. Preserve the approved schema and existing homepage and DutyWindow behavior.

New production files live under `src/main/java/com/aeroroster/persistence/entity` and `persistence/repository`. PostgreSQL integration tests live under `src/test/java/com/aeroroster/persistence`. Update README, the Phase 1 checklist and the decisions document with current status and verification instructions.

Mapping risks include string enum storage, timestamp precision, nullable qualification expiry, lazy relationship traversal, identity generation and trigger-owned audit history. Verify them against PostgreSQL using V1/V2, Hibernate schema validation, seeded repository reads, insert/update round trips, constraint rejection and transactional rollback. Run both `mvn test` and `mvn package`, then smoke-test the packaged application's existing homepage.

## Mapping decisions

- Each entity maps explicit table and column names, schema string lengths and nullability. All IDs use `Long` and identity generation. The database retains ownership of unique constraints, checks, indexes and foreign keys through Flyway.
- All foreign-key relationships use unidirectional, lazy `ManyToOne` associations. No cascading writes or removals are configured. Callers persist referenced objects explicitly. Child repositories provide collection queries.
- `CrewRole`, `FlightStatus` and `AssignmentStatus` use `EnumType.STRING` against existing VARCHAR columns. PostgreSQL continues to enforce the permitted enum values.
- `Instant` maps every TIMESTAMPTZ column. PostgreSQL has microsecond precision. Round-trip tests use microsecond values, including an offset input normalized to an instant. `LocalDate` maps the nullable `valid_until` DATE. A null expiry represents an open-ended qualification for later business-rule evaluation.
- New aircraft and crew default to active. New flights default to SCHEDULED and assignments to ACTIVE, matching the database defaults. Assignment `createdAt` is generated by PostgreSQL and retrieved by Hibernate on insertion. Java exposes no setter for that timestamp.
- `FlightAudit` is Hibernate-immutable, has a protected no-argument constructor and getter-only access. Its repository extends the minimal Spring Data `Repository` interface and exposes only reads, including paginated history access. These are application-layer protections. Database permissions remain the final boundary for arbitrary SQL clients.
- Audit `flightId` is a scalar snapshot. V1 deliberately has no audit-to-flight foreign key, allowing audit rows to survive flight deletion. The database trigger creates INSERT, UPDATE and DELETE events within the flight transaction.
- Entities use object identity without custom `equals`, `hashCode` or `toString`, avoiding mutable equality and relationship recursion. Public no-argument constructors and explicit setters keep writable entities straightforward for the student team.
- Entity access belongs inside service transactions when lazy associations are traversed. Open-in-view remains disabled. Future controllers must return DTOs. This milestone adds persistence classes only and exposes no entity response endpoints.
- Flight departure-range queries use `[start, end)` bounds and ascending departure/ID ordering. Unavailability overlap uses `startTime < end && endTime > start`, allowing touching endpoints. Callers must supply increasing bounds.
- Duty repositories accept an explicit status so callers can request ACTIVE records or examine cancellation history. Exact crew/flight/status queries return a list because the schema permits multiple CANCELLED records for the same crew/flight pair. The partial unique index restricts ACTIVE results to at most one. A regression check exercises multiple cancellations. Conflict validation, rest/duty policies, assignment orchestration and concurrency locking belong to later Java services. Future assignment, cancellation and schedule-change workflows must execute atomically with the documented stable-order locks.

## Test setup

Use a dedicated PostgreSQL 17 database called `aeroroster_test`. It was created during this implementation. For a fresh machine, run the following once using a PostgreSQL account permitted to create databases. Skip creation if it already exists.

```powershell
psql -U postgres -d postgres -c "CREATE DATABASE aeroroster_test;"
```

If using a dedicated account, create the database with that account as its owner, or have the database administrator grant it schema creation and table privileges sufficient for Flyway. Set credentials locally when the PostgreSQL authentication configuration requires them.

```powershell
$env:TEST_DB_URL = "jdbc:postgresql://localhost:5432/aeroroster_test"
$env:TEST_DB_USER = "postgres"
$env:TEST_DB_PASSWORD = "YOUR_LOCAL_PASSWORD"
mvn test
mvn package
```

The default URL/user are the values above and the default password is empty. Tests do not inherit `DB_URL`, `DB_USER` or `DB_PASSWORD`. Never commit credentials. The test context initializer checks the resolved datasource URL before datasource/Flyway startup and requires the exact database name `aeroroster_test`, without JDBC query parameters. A missing database, connection error or wrong target fails the test suite.

Flyway applies V1/V2 to an empty test database, validates migration checksums on later runs, and Hibernate validates mappings. Tests run against real PostgreSQL and each test rolls back its writes, including audit-trigger writes. PostgreSQL identity sequences can advance across rollbacks, so tests look up seeds by natural keys and never assume specific IDs. The test database retains its schema and fictional seed records. Run a single test-suite process against it at a time and keep it dedicated to this suite.

The integration suite covers all ten entity mappings and seed counts, role/active filters, aircraft lookup, qualification joins and nullable expiry, half-open flight ranges, lazy loading, assignment status filtering, interval overlap, identity-generated inserts, all role/flight/assignment enum values, UTC microseconds, database-created assignment timestamps, invalid foreign-key rejection and audit history surviving flight deletion. The original three DutyWindow tests run alongside it.
